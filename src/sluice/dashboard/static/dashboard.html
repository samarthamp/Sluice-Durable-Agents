The topology

Four OS processes, one container, one shared journal. Nothing trusts itself — the thing that acts and the thing that records ground truth are different processes.

Drawn live in the page, so it themes with everything else. Gold is whoever holds the lease, red is the one effect that cannot be undone or queried, blue is the verification path. The dashed line is the addition worth noticing: the checker reads the journal as well as the ledger — the ledger alone tells you what happened, not what was intended, and EEO is a claim about both.

Following one alert

1. sluice producer publishes to a Redis stream.
2. A consumer group hands it to whichever orchestrator asks. Delivery is at-least-once — duplicates are expected, not a bug.
3. The orchestrator derives workflow_id from the alert id, so a redelivered alert lands on the same workflow.
4. It takes a lease on that workflow. The loser does not act, and does not ack — the entry stays pending for whoever leads.
5. Every step is journaled to a shared SQLite WAL file before and after it runs. That record is what makes a crash resumable.
6. Effects go over HTTP to three services, each carrying an idempotency key and a fencing epoch.
7. Each service writes what it did to the ground-truth ledger, a fourth process.
8. The EEO checker compares journal against ledger. It is the oracle, and it is not the orchestrator.

Why the pager is the hard one

The three effect services are deliberately not equivalent. A ticket can be closed and a channel post can be deleted, so both are reversible — a mistake is recoverable. Both can also be queried, so they are observable — after a timeout you can go and find out what happened.

Paging a human is neither. You cannot un-ring a phone, and the pager exposes no endpoint to ask whether it rang. When a page times out there is no inverse to apply and nothing to probe, which is exactly why the system treats unknown as its own outcome rather than collapsing it into failed. See Edge cases → Bounded ambiguity.

Seven scenarios

Each runs against all three modes: pinned replays the journaled decision, naive re-runs the agent, sluice forks, cleans up, then acts.

The baselines aren't strawmen — they're what a reasonable engineer builds, and each fails a different EEO clause. Pick one from the dropdown on the Live tab, or run sluice demo --scenario NAME --slow 0.35.

The corners that actually decide correctness

Each is covered by a test or smoke check, not just by argument. The interesting ones are where the honest answer is "I don't know" — guessing there is worse than escalating.

Exactly-Effect-Once — the three clauses

A claim about effects, checked against the out-of-process ledger. A safety property, not a liveness one.

1 · No duplication

No irreversible effect is applied twice for one incident without a supersede annotation explaining the second.

2 · No loss

Every workflow ends with either a committed action or an escalation a human can see. Silence is a violation.

3 · Clean abandonment

An abandoned branch leaves no uncompensated reversible effect, and any irreversible residue is recorded and superseded.

Refusing to act against a broken world and saying so is not a violation — it did no work. Hence the escalation rate beside the verdict: a verdict alone goes green against a dead effect layer.

Reading the Live tab

Every element, top to bottom. The one that decides whether a run was correct is the EEO badge — everything else describes what happened, not whether it was right.

The EEO badge — read this one first

BadgeMeans
EEO PASS No effect duplicated, nothing lost, no uncompensated residue on an abandoned branch. Graded against the ledger, a different process.
EEO FAIL At least one unexplained clause violation. The clause names appear beside the badge.
EEO — No verdict on file yet. The grader writes one beside the journal when a run finishes; a journal alone cannot be graded.

A pane can escalate and still PASS. That is not a contradiction: EEO is a safety property. A workflow that refuses to act against a broken world and hands a human the details has duplicated nothing and lost nothing. compfail is exactly this case — sluice escalates, pages nobody, and passes, while naive pages someone and fails.

The gate never blocks on irreversible residue — blocking on something that can never be satisfied is a deadlock by construction. It blocks only on what can actually be compensated.

Driving it

Pick a workload from the dropdown and press Run — it executes all three modes in order and the panes fill in live. The button needs sluice dashboard --allow-control; without it the button is disabled and you drive from a terminal instead:

sluice demo --scenario poison --slow 0.35

For the distributed pane, with services and Redis up:

sluice faults poison, then sluice producer --demo --count 1, then sluice orchestrator --once --narrate

The dashboard reads journals and never drives execution. Even the Run button launches the same scenario code a terminal would — if this page dies mid-demo, the system is unaffected.
